> `PROJECT_SPEC.md`(Phase 1~3)와 `PRODUCTION_HARDENING_SPEC.md`(EP-7~8)가 "이 프로젝트에서 구현할 이슈 목록"이라면,

> 실제 금융권/대규모 트래픽 서비스가 어떻게 처리하는지 정리한 **참고 문서**다.
> 지금 바로 구현할 이슈 목록이 아니라, 면접에서 "이거보다 트래픽이 100배 몰리면 어떻게 하실 건가요?"에
> 답할 수 있도록 만드는 지식 베이스. 특정 항목을 실제로 구현하기로 결정하면, 그때 별도 TDD 구현
> 계획으로 뽑아낸다.

## 우리 프로젝트 규모 vs 실전 규모

지금 우리 코드(Phase 1)는 단일 인스턴스, 단일 MySQL, 동기 API 호출 구조다. 이 구조가 실전에서 못 버티는 지점은 트래픽 총량이 아니라 **"핫스팟"** — 특정 리소스(계좌 하나, 인기 종목 하나)에 요청이 몰리는 순간이다. IS-12/13에서 계좌 1개에 100스레드가 몰렸을 때 낙관적 락+재시도로도 100%를 못 채운 게 정확히 이 핫스팟 문제였다. 아래 내용 전부가 결국 "핫스팟을 어떻게 흡수하거나 애초에 안 만드나"로 수렴한다.

## 1. API/게이트웨이 계층

### Rate Limiting (요청 자체를 제한)
서버까지 요청이 도달하기 전에 걸러낸다. 토큰 버킷(Token Bucket) 알고리즘이 표준 — 사용자/IP별로 "초당 N개 토큰"을 채워주고, 요청마다 토큰 하나를 소비. 토큰이 없으면 즉시 `429 Too Many Requests`.
```
사용자 A: 1초에 10개 토큰 리필, 버킷 최대 20개
→ 순간적으로 20개까지는 몰아서 보내도 되지만, 그 이상은 리필 속도(초당 10개)로 제한됨
```
Redis에 `INCR` + `EXPIRE` 조합으로 구현하거나(고정 윈도), Redis + Lua 스크립트로 sliding window를 구현. API Gateway(Kong, AWS API Gateway) 레벨에서 처리하면 애플리케이션 코드는 아예 안 건드려도 됨.

### Circuit Breaker / Bulkhead (장애 전파 차단)
하나의 다운스트림(예: 원장 서비스)이 느려지면, 그걸 호출하는 모든 스레드가 같이 멈춰서 전체 서비스가 죽는 걸 막는다.
- **Circuit Breaker**(Resilience4j): 실패율이 임계치를 넘으면 회로를 "열어서" 일정 시간 동안 호출 자체를 안 하고 즉시 실패 응답 — 죽어가는 다운스트림에 요청을 더 안 보내서 회복할 시간을 줌.
- **Bulkhead**: 다운스트림별로 스레드풀/커넥션풀을 분리 — 원장 서비스 호출용 스레드 10개, 알림 서비스 호출용 스레드 10개를 따로 둬서 하나가 고갈돼도 다른 쪽은 안 죽음. 배의 격벽(bulkhead)에서 따온 이름 그대로, 한 칸에 물이 차도 배 전체가 안 가라앉게.

## 2. 애플리케이션 계층 — 수평 확장

### Stateless가 전제조건
서버 인스턴스를 몇 대로 늘리든 아무 인스턴스나 요청을 받아도 똑같이 동작해야 함 — 그래서 JWT(세션 저장소 불필요, `PRODUCTION_HARDENING_SPEC.md` IS-16)를 쓰는 것. 세션을 서버 메모리에 두면 로드밸런서가 "같은 사용자는 같은 서버로"(sticky session)를 강제해야 하고, 그 서버가 죽으면 세션이 통째로 날아감.

### Auto Scaling
쿠버네티스 HPA(Horizontal Pod Autoscaler)가 CPU/메모리/커스텀 메트릭(초당 요청 수 등) 기준으로 인스턴스 수를 자동 조절. 평소 3대, 트래픽 몰리면 자동으로 20대까지 늘어났다가 다시 줄어듦. 급증 트래픽에 대비해 최소 인스턴스 수(warm pool)를 미리 확보해두는 것도 실전에서 흔함 — 스케일아웃 자체가 몇 분 걸리므로 트래픽 터진 직후엔 이미 늦음.

## 3. 캐싱 계층

### Cache-Aside (가장 흔한 패턴)
```
조회: Redis에서 먼저 찾음 → 없으면 DB 조회 → Redis에 채워넣고 반환
갱신: DB 갱신 후 해당 캐시 키 무효화(삭제) — 캐시에 새 값을 바로 쓰지 않고 지우기만 하는 이유는
      "DB 갱신 성공 + 캐시 쓰기 실패"로 캐시와 DB가 어긋나는 걸 피하기 위함(다음 조회 때 다시 채워짐)
```
잔고 조회, 종목 시세 조회(Phase 2)처럼 "쓰기보다 읽기가 압도적으로 많은" 데이터에 적합. 반대로 계좌 `balance`처럼 정합성이 생명인 데이터는 캐시를 두더라도 **쓰기 경로는 항상 DB가 source of truth**로 남기고, 캐시는 읽기 가속에만 씀.

### Cache Stampede 방지
인기 데이터의 캐시가 동시에 만료되는 순간, 수천 개 요청이 한꺼번에 DB로 몰리는 현상. 해결책:
- TTL에 랜덤 지터를 섞어서 만료 시점을 분산 (`TTL = 600 + random(0, 60)`초)
- 첫 번째 요청만 DB를 조회하게 락을 걸고, 나머지는 그 결과를 기다림(요청 병합)

## 4. 메시징/이벤트 계층 (Kafka)

### 파티셔닝으로 동시성 자체를 없앰
`docs/PRODUCTION_HARDENING_SPEC.md` EP-8 IS-24에서 이미 다룬 내용 — 계좌 ID를 파티션 키로 쓰면 같은 계좌의 이벤트는 항상 같은 파티션, 같은 컨슈머가 순서대로 처리. DB 락/재시도 없이 애플리케이션 레벨에서 직렬화가 끝남.

### Transactional Outbox 패턴
"DB 갱신"과 "이벤트 발행"을 하나의 원자적 단위로 묶는 문제. `DB commit은 성공했는데 Kafka 발행이 실패`하거나 그 반대 상황(둘 사이에 진짜 분산 트랜잭션을 걸 수는 없음)을 막기 위한 표준 해법:
```
1. 같은 DB 트랜잭션 안에서 비즈니스 테이블 UPDATE + outbox 테이블에 이벤트 INSERT (둘 다 로컬 트랜잭션이라 원자적)
2. 별도 프로세스(폴러 또는 CDC: Debezium)가 outbox 테이블을 읽어서 Kafka로 발행
3. 발행 성공하면 outbox 행 삭제/표시
```
이렇게 하면 "DB엔 반영됐는데 이벤트는 안 나감" 같은 반쪽짜리 상태가 원천적으로 불가능해짐 — 이체 이벤트를 다른 서비스(알림, 정산)에 전파해야 하는 Phase 2/3에서 중요해짐.

### Backpressure
컨슈머가 처리 속도를 못 따라가면 무작정 쌓아두지 말고(Consumer Lag 폭증), 컨슈머 인스턴스를 늘리거나(파티션 수만큼 수평 확장 가능) 프로듀서 쪽에서 발행 속도를 조절.

## 5. 데이터베이스 계층

### Read Replica (읽기/쓰기 분리)
잔고 조회, 거래 이력 조회(IS-11) 같은 읽기 트래픽을 복제본으로 분산하고, 쓰기(입출금/이체)만 마스터로 보냄. 복제는 비동기라 **복제 지연(replication lag)** 이 생길 수 있음 — "방금 이체했는데 조회하니 반영이 안 됨" 문제가 생길 수 있어서, 쓰기 직후 조회는 마스터로 보내는 라우팅 규칙이 필요(read-your-own-writes 보장).

### 샤딩 (Sharding)
테이블 하나가 너무 커지거나 쓰기 트래픽이 단일 마스터로 감당이 안 될 때, 계좌 ID 기준으로 데이터를 여러 DB 인스턴스에 분산.
```
account_id % 4 == 0 → 샤드 A
account_id % 4 == 1 → 샤드 B
...
```
대가: 샤드를 넘나드는 조인/트랜잭션(예: 서로 다른 샤드의 두 계좌 간 이체)이 어려워짐 — 이체처럼 "두 계좌를 원자적으로 묶어야 하는" 연산과 정면으로 부딪히는 트레이드오프라, 도입 전에 "샤딩 키를 뭘로 잡아야 이체가 안 깨지는가"부터 설계해야 함(예: 같은 사용자의 계좌는 항상 같은 샤드에 두기).

### Connection Pooling 튜닝
HikariCP 풀 크기를 무작정 키운다고 처리량이 느는 게 아니라, DB의 실제 동시 처리 능력(CPU 코어 수 기준)을 넘는 순간 대기 시간만 늘어남. `pool size = ((core_count * 2) + effective_spindle_count)` 같은 경험식이 있고, 실무에서는 PgBouncer/ProxySQL 같은 커넥션 풀러를 DB 앞에 둬서 애플리케이션 인스턴스 수가 늘어나도 DB에 붙는 실제 커넥션 수는 상한선 안에 묶어둠.

### CQRS (Command Query Responsibility Segregation)
쓰기 모델과 읽기 모델을 아예 분리 — 쓰기는 정규화된 원장 테이블에, 읽기는 조회 전용으로 비정규화된 뷰(또는 별도 read DB)에. `IS-23`(원장 append-only 전환)이 사실 CQRS의 축소판: 원장(append-only, 쓰기 최적화)과 잔고 조회(합계/캐시, 읽기 최적화)를 분리하는 발상이 같음.

## 6. 배치/정산 계층

실시간 API 뒤에서, 실제 은행 시스템은 매일 밤 대규모 배치 작업을 돌린다.
- **정산/대사(Reconciliation)**: 하루치 거래를 다시 집계해서 원장 합계와 실제 잔고가 일치하는지 검증 — 실시간 처리 중 놓친 정합성 오류를 여기서 잡아냄.
- **계정계 vs 정보계 분리**: 한국 금융권 특유의 구조. 계정계(실제 잔고/거래를 처리하는 코어 시스템, 무조건 정확해야 함)와 정보계(리포트/분석용, 계정계에서 배치로 데이터를 넘겨받아 처리)를 물리적으로 분리 — 무거운 분석 쿼리가 실시간 거래 처리 DB에 부하를 주지 않도록.
- 배치는 보통 Spring Batch + 스케줄러(Quartz)로 청크 단위 처리, 실패 시 재시작 지점(체크포인트) 관리.

## 7. 관측성 계층

### 분산 트레이싱
마이크로서비스로 쪼개지면 요청 하나가 여러 서비스를 거치는데, `PRODUCTION_HARDENING_SPEC.md` IS-19의 Correlation ID만으로는 "어느 구간에서 얼마나 걸렸는지"까지는 못 봄. OpenTelemetry + Jaeger/Zipkin으로 요청 하나의 전체 호출 경로를 트리 형태로 시각화 — "이체 API가 500ms 걸렸는데, 그중 400ms가 원장 서비스 호출이었다"까지 추적 가능.

### 메트릭 + 알람
IS-20(Actuator + Prometheus)에서 TPS/에러율/지연시간을 노출하는 것에 더해, 실전에서는 임계치를 넘으면 자동으로 온콜에게 알람(PagerDuty, Grafana Alerting)이 가도록 연결. 특히 금융권은 "에러율 급증"보다 "정상 응답인데 잔고가 이상한 패턴"(이상 거래 탐지) 같은 비즈니스 메트릭 알람도 따로 둠.

## 8. 장애 대응 / 복원력

### Timeout + Retry + Idempotency는 항상 세트
Retry만 있고 Idempotency(`PRODUCTION_HARDENING_SPEC.md` IS-18)가 없으면 재시도가 중복 처리를 유발함 — "네트워크 타임아웃이라 재시도했는데 사실 원래 요청은 서버에서 처리 완료됨" 시나리오가 이체 중복 사고의 전형적 원인.

### Failover / DR (Disaster Recovery)
- **RTO**(Recovery Time Objective, 목표 복구 시간)와 **RPO**(Recovery Point Objective, 목표 복구 시점 — 얼마만큼의 데이터 유실까지 허용하나)를 먼저 정의.
- Active-Active(여러 리전이 동시에 트래픽 처리, 복잡하지만 무중단) vs Active-Passive(평소엔 대기, 장애 시 전환 — 단순하지만 전환 시간 발생) 중 서비스 중요도에 따라 선택.
- 금융권은 RPO를 0에 가깝게 요구하는 경우가 많아서(거래 데이터 유실 절대 불가), 동기 복제(synchronous replication)를 일부 구간에 쓰기도 함 — 대신 그만큼 쓰기 지연이 늘어나는 트레이드오프.

## 면접 예상 질문

- 지금 구조에서 트래픽이 100배로 늘면 제일 먼저 뭐가 터지나요? → 단일 MySQL 마스터의 쓰기 처리량과, 인기 계좌/종목에 대한 락 경합(IS-12에서 실제로 관측). 첫 대응은 읽기 트래픽을 Read Replica로 빼서 마스터 부하를 줄이는 것, 그다음이 Kafka 파티셔닝으로 핫스팟 자체를 없애는 것.
- 캐시를 도입하면 정합성은 어떻게 지키나요? → 잔고처럼 정합성이 생명인 데이터는 캐시를 read-through로만 쓰고 쓰기는 항상 DB(source of truth)로, 갱신 시 캐시는 새 값을 쓰는 대신 무효화(삭제)만 해서 DB-캐시 불일치 가능성을 최소화.
- 재시도와 멱등성이 왜 항상 같이 가야 하나요? → 재시도는 "요청이 서버에 도달했는지 클라이언트가 확신 못 하는 상황"에서 발생하는데, 멱등성이 없으면 실제로는 처리된 요청을 중복 처리하게 됨 — 이체 중복 처리가 대표적 사고 유형.
- 샤딩을 도입하면 이체 로직이 왜 깨지나요? → 두 계좌가 서로 다른 샤드에 있으면 하나의 DB 트랜잭션으로 원자적으로 처리할 수 없음. 같은 사용자의 계좌를 항상 같은 샤드에 두거나, Saga 패턴(보상 트랜잭션)으로 분산 트랜잭션을 흉내내야 함.
