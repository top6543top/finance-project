# 거래 API 변경 계약

## 금액

입금·출금·이체 금액은 양수, 소수 두 자리 이하, 최대 99999999999999999.99입니다. 0.015를 반올림하여 처리하지 않고 400/C001로 거절합니다. 계좌 잔액이 같은 DECIMAL(19,2) 상한을 넘는 거래는 409/C018입니다. 운영 업무 한도나 통화별 최소 단위는 별도 정책입니다.

## 멱등성 키

거래 POST에는 Idempotency-Key가 필요합니다. 영문 대소문자·숫자·`.`·`_`·`:`·`-` 조합 1~100자만 허용합니다. 새 키는 대소문자를 구분합니다. 키의 범위는 로그인 사용자별입니다.

| 요청 | 결과 |
|---|---|
| 같은 사용자 + 같은 키 + 동일 작업/계좌/금액 | 기존 응답 재생, 추가 원장 없음 |
| 같은 사용자 + 같은 키 + 금액/작업/계좌/수취인 변경 | 409/C017 |
| 다른 사용자가 같은 문자열 키 사용 | 자신의 권한과 별도의 요청으로 처리 |
| 이전 버전에서 저장한 키 또는 당시 비교 규칙상 동등한 키 | 409/C017, 운영 확인 필요 |
| 일시적 DB 충돌 5회 후에도 실패 | 409/C010, 부분 반영 없이 종료 |

1, 1.0, 1.00은 동일한 금액으로 정규화합니다. 요청 지문에는 금액뿐 아니라 작업 종류와 관련 계좌가 포함됩니다. 성공 후 응답을 받지 못했다면 같은 키와 같은 내용을 재전송합니다. C017에 대해 새 키로 자동 재전송하면 중복 거래가 될 수 있으므로 기존 거래를 먼저 확인합니다.

기존 키의 사용자·원래 요청을 추측하여 이관하지 않습니다. legacy_key는 기존 DB 문자 비교 규칙을 유지하며, 해당 키의 과거 응답을 다른 사용자에게 공개하지 않습니다. 키는 TTL로 임의 삭제하지 않습니다.

## 응답과 조회

입금·출금·이체 응답은 기존 필드에 transactionId, actorId, idempotencyId를 추가합니다. transactionId는 원장 행 ID이며 재생 요청에서 바뀌지 않습니다. 이전 거래 이력에는 새 감사 필드가 null일 수 있습니다.

기존 GET /api/accounts/{accountNumber}/transactions는 고정된 id DESC 순서를 사용하고 size는 1~100입니다. 사용자가 지정한 sort로 변경하지 않습니다. 동시 추가 중 offset 페이지에는 이동 현상이 있을 수 있으므로 연속 탐색에는 새 커서를 사용합니다.

```text
GET /api/accounts/{accountNumber}/transactions/cursor?size=20
GET /api/accounts/{accountNumber}/transactions/cursor?size=20&beforeId=123

data: { items: [...], nextCursor: 103, hasNext: true }
```

다음 요청에는 반환된 nextCursor를 전달합니다. hasNext=false이면 탐색을 끝냅니다. 커서는 ID 경계 아래의 이력을 탐색하며, 전역 시점의 불변 스냅샷이나 늦게 커밋된 모든 거래의 완전한 포착을 보장하지 않습니다. 모든 조회에 계좌 소유자 검사가 적용됩니다.

## 운영 보안 경계

- prod의 모의 입금은 인증한 계좌 소유자라도 403/C019입니다.
- Redis 제한 서비스 장애는 503/C020과 Retry-After를 반환합니다. 실제 한도 초과는 429/C016입니다.
- 만료·서명 오류·잘못된 주체의 JWT는 401로 처리합니다.
- 비밀번호는 BCrypt의 UTF-8 72바이트 한도를 검사합니다. 글자 수와 바이트 수가 다를 수 있습니다.
- GET /livez, /readyz만 공개 프로브입니다. 운영 Swagger와 기타 관리 경로는 익명 공개하지 않습니다.

API 소비자는 추가 응답 필드, 고정 이력 정렬, 키/금액 검증 강화, 운영 모의 입금 비활성화와 Redis 장애 시 거절 동작을 반영해야 합니다.
